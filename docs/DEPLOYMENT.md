# Import, deploy, and verify

**Current status:** source and configuration are provided; there is no created GitHub repository, provisioned hosting service, or verified public URL. No deployment charges have been incurred by these files.

## 1. Review locally

Run the README commands with `PROVIDER=demo`. Exercise Individual review and Batch review. This mode only accepts bundled synthetic images and is not the final arbitrary-upload assessment configuration.

## 2. Create the source repository

Create an empty GitHub repository in your account. Public is easiest for reviewers; a private repository requires granting them access. Do not initialize the remote with conflicting starter files.

In the extracted `label-review` directory:

```bash
git init -b main
git add .
git commit -m "Implement label verification and CSV review workflow"
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
git push -u origin main
```

Replace the uppercase placeholders. Sign in with your usual GitHub-supported authentication. Do not paste access tokens into chat, source code, commit messages, or the remote URL. `.env.example` contains placeholders; the real `.env` must stay untracked. Confirm with `git status` before pushing.

The included CI workflow runs Python/Node tests, installs frontend packages, builds with Vite, and exercises the app in a normal Chromium browser. It has not run on GitHub yet. After the first connected `npm install`, inspect and commit `frontend/package-lock.json`; change the install step to `npm ci`. Rebuild `frontend/dist` before deploying frontend changes.

## 3. Deploy on Render

Connect Render to your repository, choose a new Blueprint, and select this repository's `render.yaml`. Review the configuration before applying it:

- One Python web service serves both the API and the included static frontend.
- The plan is `1c-2g`, **paid compute**. Check the current price and approve it in your own account. You may select another adequate always-on plan after testing. The configuration alone does not spend money.
- Set `OPENAI_API_KEY` when prompted. Live mode is selected; sample mode is not the public default.
- `REVIEW_ACCESS_TOKEN` is generated by the platform. Retrieve it from the service's environment settings and privately provide it to authorized reviewers.
- Health path: `/api/ready`; startup: `python scripts/run.py --host 0.0.0.0`; the script reads the platform's `PORT`.
- Automatic deployments are off. Deploy explicitly after tests pass and source/static builds are synchronized.

Render's [Blueprint reference](https://render.com/docs/blueprint-spec) documents these fields and secret handling. Free services have idle spin-down behavior, which is unsuitable for assuming a consistently fast first response; see [free service limitations](https://render.com/docs/free). No performance guarantee follows from buying a plan.

`/api/ready` checks configuration presence, **not** whether the provider key has quota or permission. Actual inference must be tested after deployment.

## 4. Perform the live acceptance checks

Use a fresh browser session against the actual HTTPS URL. Confirm the **LIVE AI** banner, enter the shared review code, and verify that arbitrary JPEG/PNG uploads reach the image service rather than sample fixtures. Do not ask Treasury to supply its own provider key.

Check at least: a clean front/back pair, a wrong ABV, a one-character warning error, an unreadable warning, a missing back image, an imported product, and a small CSV batch. Then use a label not included in the samples and inspect the extracted text manually. Confirm that provider errors do not become matches and that missing/ambiguous text stays under review.

Set the shared review token in the shell running the evaluator (not the AI key):

```bash
# Use your shell's secret-management method; do not commit the value.
export REVIEW_ACCESS_TOKEN='YOUR-PRIVATE-REVIEW-CODE'
python scripts/evaluate.py --url https://YOUR-SERVICE.onrender.com --runs 3 --output reports/live-evaluation.json
```

The URL above is a placeholder, not a created service. Live requests incur provider usage. Review the report's failures, scenario checks, and median/p95 times. It is a small synthetic smoke evaluation, not a production accuracy estimate. Test after idle periods and with real reviewer-sized images. Record cold/warm conditions and model name. A loading animation is not a five-second result.

Only after these checks pass should you add the **real** repository and application URLs to the submission. If latency exceeds the target, report the measured limitation and address it rather than labeling it compliant.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Sample-only error on a new image | The server is still in demo mode; configure and restart live mode. |
| Live banner says unavailable | `OPENAI_API_KEY` is absent on the server. |
| Provider credentials rejected | Key validity, account/model permissions, and provider quota. Never send the key to the frontend. |
| 401 access required | Use the separate review access code from hosting environment settings. |
| 429 busy/rate limited | Retry later; reduce parallel clients; inspect provider quota and the app's per-process limit. |
| Provider unreachable | The backend needs outbound HTTPS to the fixed provider endpoint. This does not bypass a restricted agency network. |
| Old UI after a frontend edit | Rebuild and commit `frontend/dist`, then redeploy. |
| Missing static entry point | Rebuild the frontend; keep the entire `dist` directory in the deployment. |
| Review needed for printed size on a good label | Expected behavior: pixel images alone do not establish physical type size. |
